Autopilot runs as an ordinary Tori chat session that reads a queue of work,
issues to ship, pull requests to review, and starts a worker session per
item. It never edits code itself, and nothing it does leaves your machine
without you approving it first: opening a pull request, submitting a review,
and merging are each their own approval, spent once, tied to the exact draft
shown to you.

## Turn it on and start it

<Steps>

1. Open Settings (the gear in the title bar) > **Autopilot** and turn on **Enable autopilot**.
   A **Cockpit** and **Workspace** switch appears in the title bar.
2. Click **Cockpit**, or press `Cmd+Shift+J`, to switch to the Cockpit.
3. Click **Set sail**. The autopilot's own session starts, on the agent, account
   and model in **Autopilot model**.
4. Tell it what to do in **Tell the autopilot...**, for example `work on #60`,
   `review https://github.com/hooli/api/pull/52`, or `work on #482 and #214,
   then #215`.

</Steps>

**Drop anchor** stops it. Its session closes; the queue on disk and every
worker stay as they are, and the workers go back to being ordinary sessions
that notify you themselves. Set sail again and it picks up the same queue.

Once started, the autopilot starts again by itself when Tori launches, until
you drop anchor. Only you can start or stop it, from the Cockpit, a shell
(`tori autopilot start`) or a paired phone; no agent session can.

Turning **Enable autopilot** off stops it and hides the Cockpit.

## Per-project contract

Each project autopilot works in has a contract: how work ships (a pull
request, or just a local branch), how far it goes before asking you
(asking before every step, or going ahead alone on anything that stays on
the machine), and whether it queues new work on its own or proposes it and
waits. A project with no contract set runs on the cautious defaults: pull
request, ask before everything.

| Term | Choices | Default |
| --- | --- | --- |
| How work ships | A pull request, or a local branch only | Pull request |
| How far it goes | Ask before everything, or go ahead alone until something would leave the machine | Ask before everything |
| Picking up work | Propose and wait, or start on its own | Propose and wait |
| Workers run on | The agent, account and model you pick for this project | Not set |
| Where issues come from | The project's own repo, or the issue sources you list | Issues assigned to you in the project's repo |

Tell the autopilot how a project should work and it records the contract,
or set it yourself in **Settings > Autopilot**, under **Projects**: pick the
project, then its choices. Each choice saves as soon as you pick it.
**Workers run on** picks the agent, account and model the same way the
autopilot's own model is picked. From a shell, use
[`tori autopilot project`](/docs/automation/cli/#autopilot).

### Issue sources

A project's work does not have to live in its own repo. If you keep tickets
in a separate repo, maybe one shared by several projects, give the project
one or more issue sources. Each source is a repo plus what an issue there
has to match:

| Field | What it matches |
| --- | --- |
| Repo | The repo the issues live in, as `owner/name`. Required. |
| Labels | Every one of these labels. |
| Exclude labels | None of these labels. |
| Milestone | This milestone. |
| Assignee | Left out, issues assigned to you. `any` is anyone, or give a login. |
| Extra | Raw GitHub search qualifiers added after the rest, such as `sort:created-asc`. |

Labels and milestones can have spaces and colons in them, for example
`block 1` or `Phase 1: Mac and Android`. Only open issues are matched.

Once you set sources they replace the default, so if you still want issues
from the project's own repo, add it as a source too. Review requests always
come from the project's own repo. A source whose repo is not `owner/name` is
refused, because a search with no repo in it would read every repo your
account can see.

An issue from another repo is named by its repo, such as
`gettori/tickets#31`. An issue in the project's own repo stays `#31`.
Starting one links its branch to the issue in the other repo, while the
branch itself is made in the project's repo. Its suggested branch name
leads with that repo's name, such as `tickets-31-dogfood`, so it never
collides with the project's own issue 31.

Set sources in **Settings > Autopilot**, under **Projects**. **Add source**
gives you a blank one to fill in. Labels and exclude labels are comma
separated. **Remove source** takes one out. Nothing changes until you press
**Save sources**, which saves the whole list at once. If a source is refused,
for example because its repo is not `owner/name`, the list stays as you typed
it and the reason shows below the list. With no sources, the editor says the
project reads the issues assigned to you in its own repo.

You can also use the `--issues` flag of
[`tori autopilot project`](/docs/automation/cli/#autopilot), or ask the
autopilot to set them:

```sh
tori autopilot project --issues '[{"repo":"gettori/tickets","milestone":"Phase 1: Mac and Android"}]'
```

## The queue

Work items are either **ship** (take an issue to a pull request or a local
branch) or **review** (review someone else's pull request). Autopilot can
pick these up on its own from your assigned issues and review requests, or
you can hand it one directly. Every item you see in the Cockpit, in flight,
waiting, done, or failed, is one of these.

To hand it work, type in the Cockpit's composer, for example
`work on #60`, or ask it to review a pull request. For a ship item it reads
the issue, titles the item, links a
branch to the issue, makes the worktree, starts a worker on the project's
picks, and brings you a pull request to approve. A review item runs the
same way, to one review for you to approve.

With pickup on, each poll of the host reads the project's issue sources,
or with none your assigned issues in its repo, plus your review requests.
The first poll of a project, or of a source that is new or was just edited,
only proposes, so an old backlog never starts itself. An issue that two
sources both match becomes one item. An issue another project already has
open is left to that project.

When an issue leaves every list (it closed, it was unassigned, or it no
longer matches its source), an item that has not started yet closes. An
item already running is not stopped. It gets a note saying so, and the
autopilot asks you whether to stop it. If a source fails to answer, or
comes back with as many issues as one search can hold, nothing closes on
that poll, since a missing issue proves nothing then.

The queue is on disk. Quit Tori and relaunch, and the same items are there;
an approval nobody answered comes back pending. An item closes itself when
its pull request merges.

Every reference the autopilot shows reads as a number and a place: the
number opens the issue or pull request on the host, the place opens that
worktree with the worker's tab.

## Approvals

Nothing leaves the machine on the autopilot's say. Opening a pull request,
submitting a review and merging each wait on a card, and the card shows
exactly what would be posted: the title, branches and body of a pull
request; the verdict and every line comment of a review; the method and
head commit of a merge. You can approve it, edit it, reply to the worker,
or dismiss it.

An approval is spent once and is tied to that exact draft and commit. If the
branch moves after you approve, the push is refused rather than sending
something you did not read.

A worker's permission prompts are not the autopilot's to answer. They wait
for you, on the card or on a paired phone. A worker's questions do reach the
autopilot, which may answer the ones it can and brings you the rest.

## While it runs

- Workers are locked while the autopilot drives them: nothing to type into,
  nothing to close. Stop the autopilot and they go back to being ordinary
  sessions that notify you themselves.
- Waiting costs no tokens. The autopilot is woken by Tori, not by polling,
  when a worker asks a question, wants a permission, ends, goes idle,
  stalls, or its pull request changes.
- A worker that sits silent mid-turn past **Worker stalled after** is
  flagged as stalled.
- Starting the autopilot resumes its last session. If that session died, or
  you changed its agent, it starts a fresh one that picks up the same
  workers, holds and cards.
- No agent session can turn the autopilot on or off. Only you can: from the
  Cockpit, a shell, or a paired phone.

The Cockpit has three columns:

- **Crew on deck**: the workers running now, each a card ringed in the colour
  of its state, with its issue number, title and place (`work -> api ->
  feat/webhooks`), the last lines of its log, and what it is doing. **Watch**
  opens the worker's session. Under it, **Waiting at the dock** lists queued
  items, with what each waits for.
- **The middle**: a banner saying where things stand, the autopilot's own chat,
  and its composer. Decision cards appear in the chat under **Captain's call**.
- **Ship's log**: what happened, newest last, with what needs you marked.

The banner plays one of six scenes picked from the local hour, dawn to night,
and turns to a storm when more workers are out than **Workers at once**
allows. With nothing to do it says **The deck is quiet. Hand the autopilot a
ticket or a PR.**

Leaving the Cockpit detaches from the autopilot's session without closing it.

### Decision cards

Anything that needs your call is a card:

| Card | Asks |
| --- | --- |
| **PR** | Open this pull request: title, branches and body |
| **Review** | Submit this review: verdict, body and every line comment |
| **Merge** | Merge with this method at this commit |
| **Question from worker** | A worker's question the autopilot could not answer |

Each has **Approve**, **Edit**, **Reply** and **Dismiss**. **Edit** lets you
change the draft before approving; **Reply** answers the autopilot in the chat;
**Dismiss** declines.

### The popup

`Cmd+L` opens the autopilot as a popup over your workspace, without leaving
it: what is **In flight**, the **Decisions** waiting on you, and a composer. Its
header says how things stand, for example **Working on 2, 2 decisions**. The
expand button opens the full Cockpit. `Escape` or a click outside closes it.

### Sessions the autopilot drives

A worker the autopilot is driving cannot be typed into: its composer is
replaced by a bar, **The autopilot has this session**, saying what it is doing
now, with **Back to autopilot** and **Stop to type**. Stopping to type stops the
whole autopilot, which hands every worker back to you. Workers cannot be closed
or deleted while it drives them.

## Settings

Settings > **Autopilot**:

| Setting | Default | What it does |
| --- | --- | --- |
| **Enable autopilot** | Off | Shows the Cockpit switch. Off stops the autopilot and hides it |
| **Autopilot model** | Claude | The agent, account, model and effort the autopilot's own session runs on |
| **Worker stalled after** | 20 minutes | How long a worker may sit silent mid-turn before the autopilot hears it stalled. Waiting on your answer does not count |
| **Workers at once** | 2 | How many workers run at a time, kept one under **Warn above** in Settings > Chat. The rest wait at the dock |
| **Compact at context** | Agent decides | A context percentage past which Tori sends `/compact` between the autopilot's own turns |

Workers run on each project's own picks; see [Per-project contract](#per-project-contract).
